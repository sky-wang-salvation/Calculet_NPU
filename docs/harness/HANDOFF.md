# DeepSeek Harness 方案交接

## 1. 给下一位协作者的起点

先读 [README](README.md) 与 [本机开发交接](local-development.md)，再读 [讨论与取舍](discussion-and-decisions.md)。用户随后授权开始本机开发，第一版插件已实现；最终用户场景仍未确定。

用户方向：做 DeepSeek Harness 与少见 NPU 的桥梁；需要能使用已部署模型，也能利用适配知识推进新模型。用户反复要求真实使用场景，并明确否定将固定安装、补丁或记忆封装当成主要独立价值。

**最终用户任务尚未定。** 分镜、仿真补测、资料问答都是助手候选；不得默认用户已经选定分镜产品，或默认认可某种商业定位。

## 2. 不要重复的讨论弯路

- 不再用“自动安装模型、少敲命令、记住修复”作为全部产品价值。
- 不把多写几个 Skills 或给记忆起新名字当作 RSI 成绩。
- 不同时扩展三个应用，也不把五题当作必须全部完成。
- 不宣称 NPU 天然更快、完整模型已跑通、模型具备未验证的模态或训练能力。
- 不把两种 Cosmos 型号、MoT 与 MoE、研究估算与设备实测混用。

## 3. 下一步应拿到的具体定义

| 待定项 | 应形成的结果 |
| --- | --- |
| 第一位用户 | 一个具体角色、实际任务、当前替代方法 |
| 第一项产物 | 用户能检查的完整结果，不仅是服务或工具启动 |
| 采用理由 | 比当前方式少了哪些工作或错误，哪项可量化 |
| NPU 阶段 | 对应模型、核心子图、支持边界、执行证据 |
| 学习输入与指标 | 正常反馈/错误、影响的决策、保留任务和回退 |
| 范围与前提 | 模型验收状态、真实接口、时间和资源 |

插件基础连接层先按用户授权实现。扩展应用与反馈学习前仍需填写一页场景表。能否由确定性脚本完成，也应作为方案取舍条件。
