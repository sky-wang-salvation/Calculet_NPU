# 题一：融合算子开发与性能优化

## 背后的技术问题

题目要求按接口融合连续计算，比较正确性、速度、内存和搬运。分析上，核心是消除连续小算子之间的中间缓冲、布局转换和启动同步，让硬件计算能力转化为实际效率。[赛题](../../赛题选择.md)

以残差与 RMSNorm 为说明例子：

```text
z = x + residual
y = z * rsqrt(mean(z*z) + eps) * weight
```

真实题目可能要求其他归一化、额外返回 z 或不同累加精度，必须以接口为准。

假设各张量 N 个元素、每元素 b 字节，忽略权重和统计量：独立执行至少读 x/residual、写 z、读 z、写 y，约 5Nb；z 只在片上可约为 3Nb；若还需返回 z，则约为 4Nb。跨 tile 归约和片上容量不足会增加流量，不能据此直接宣称实测加速比。

Triton 融合教程与 FlashAttention 论文都说明围绕存储访问组织计算的重要性。可以借鉴 IO 分析，不移植其 GPU 性能结论。[融合 softmax 教程](https://triton-lang.org/main/getting-started/tutorials/02-fused-softmax.html)、[FlashAttention](https://arxiv.org/abs/2205.14135)

## 真实难点

| 难点 | 需要回答 |
| --- | --- |
| 归约 | 一行跨 tile 后，统计量在哪合并？ |
| 数值 | epsilon、累加、低精度中间舍入如何保持？ |
| 布局 | 相邻运算能否直接共用数据排列？ |
| 片上容量 | 融合后活跃数据增加，是否产生溢出或并行度下降？ |
| 生命周期 | 中间结果是否还被其他节点消费？ |
| 形状 | decode 与多 token 是否需要不同策略？ |
| 图接入 | 上层能否选中融合路径，未支持形状如何处理？ |

## 原粒实现路线

SDK 已有归一化和逐元素模板，可先复用片段组成 kernel，再检查 calDNN 引擎如何一次覆盖相邻运算。只减少主机函数调用不一定减少设备访存。[SDK 分层与缺口](03-sdk.md)

三层交付：独立参考和输入生成 → 融合 kernel 与边界测试 → 图引擎及样例接入。优化顺序建议是消除冗余读写、调整 tile、减少启动，然后再研究搬运重叠与多芯粒分工。

**最小成果**：一个指定模式、明确 shape/dtype、可运行样例、正确性测试和融合/未融合 NPU 对照。

**更强成果**：按形状选策略、图注册、模型集成，以及说明性能改善/退化的边界。

## 验收重点

- 零值、常量、正负抵消、极端有限数、非对齐长度。
- 接口允许的 in-place/alias；不允许时明确拒绝。
- 原始 NPU 与融合 NPU 的设备时间、端到端时间、workspace。
- 访存字节区分理论账与硬件计数器。
- 同一输入、精度、输出合同；不能靠少输出或改精度获得加速。

最有说服力的结果是说明具体减少哪些读写、图确实采用新实现、哪些形状收益成立，并验证整模型是否受益。
