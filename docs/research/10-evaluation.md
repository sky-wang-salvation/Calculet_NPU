# 正确性、性能与 NPU 贡献归因

## 先固定实验合同

记录设备编号、单/双芯粒、主机 CPU/RAM、实际连接、系统、驱动/固件、SDK 提交、编译器及运行时、模型 revision、权重 hash、输入 hash、dtype、shape、布局、精度容差和随机种子。所有数字标明单位；未知项写“未确认”。

赛题已经要求区分编译、加载、预热、推理时间，以及真机、仿真和估算。本项目建议把每个结果明确标成下列之一：

- `hardware`：实际真机执行。
- `simulation`：模拟/解释执行，不与真机耗时混算。
- `estimate`：理论估算，写出假设。
- `not_run`：尚未测试，不填写虚构数值。

## 正确性分三类

**数值算子**：相同语义的独立参考；报告最大绝对误差、适当的相对误差和错误位置。近零值不能只用相对误差。容差按比赛指定；不能以“图看起来一样”代替验收。

**选择/采样**：选择集合、顺序和并列值按合同精确检查；采样增加分布与置信区间评估。若要求逐位一致，则必须固定整个数值和随机合同。

**应用任务**：固定测试集、标签与质量指标，和 CPU/原始算法做公平对照；模型更换、量化变化、输入截断等单独列为实验变量。

## 计时边界

| 时间项 | 建议记录内容 |
| --- | --- |
| 编译 | Rust 设备编译与 docc 编译分别记录，说明缓存命中 |
| 加载 | 权重转换、传输、设备初始化和模型加载 |
| 预热 | 次数、是否达到稳定状态、是否纳入报告 |
| 设备执行 | SDK 支持的事件/计数器或有同步保证的计时 |
| 数据传输 | H2D/D2H、跨芯粒传输、字节数与测量方法 |
| 端到端 | 从同一业务入口到结果可用，含必需 CPU 处理 |

异步提交后立刻停止主机计时，可能只量到入队时间。用 SDK 指定的等待完成机制确保边界准确；不猜测可用的同步 API。存在重叠时，不能把各段时间简单相加当成端到端时间。

重复次数按噪声、运行时长和现场时段决定，报告样本数、P50/P95 及离散程度。微秒级算子可循环测量，但需说明缓冲是否常驻、缓存是否被复用。结果包括变慢和失败的输入，避免只挑最优 shape。

## “真的用了 NPU”需要怎样的证据

1. **执行证据**：官方运行日志、kernel/图作业标识、trace 或设备计数器。
2. **分工证据**：每个核心阶段在哪个处理器执行，哪里有 CPU 回退。
3. **对照证据**：相同输入与输出合同下，切换该阶段的 CPU/原始实现，比较结果和端到端时间。

算子数量占比不是性能贡献。一个很耗时的 CPU 阶段可能抵消大量 NPU 算子的收益。定义并分别报告覆盖率（按算子/计算量等口径）、时间占比、端到端加速比，不把它们合并成一个含糊的“NPU 贡献百分比”。

ONNX Runtime 官方故障排查也提示 CPU 回退可能影响性能；这是异构执行的一般参考，并不证明原粒使用同一运行时。[官方说明](https://onnxruntime.ai/docs/performance/tune-performance/troubleshooting.html)

## 用 Amdahl 公式检验宣传数字

若原系统中被优化的部分占比为 f，该部分加速 s 倍，且其他开销不变，则：

```text
端到端加速比 = 1 / ((1 - f) + f / s)
```

示例：若采样原先占 10%，即使采样加速 10 倍，端到端也只有约 1.10 倍。新增搬运/同步会进一步降低收益；移除这些开销则需要把它们纳入被优化部分重新计算。这是数学示例，不是对设备的测量。

## 功耗与多芯粒测试

功耗报告明确测点（整机墙插/板卡/芯片传感器）、采样周期、空闲基线、任务时长与温度。优先报告完成固定任务的能量，瞬时功率低不一定总能耗低。无法取得可靠读数时写“未测”，不能用 30/75 W 标称值代替。

如可在同一主机同一配置下切换单/双芯粒：记录 T1、T2，速度比 S=T1/T2，双芯粒扩展效率 E=S/2，同时检查准确性、容量和跨芯粒通信。如果是树莓派整机与工作站整机的对比，只能报告整机差异。
