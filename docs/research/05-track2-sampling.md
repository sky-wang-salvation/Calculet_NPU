# 题二：选择与采样算子

## 为什么单独出题

每个生成 token 都可能经历 logits、候选过滤、采样和下一步输入。矩阵计算之外的排序、扫描和主机同步也会影响总延迟。潜在价值是补齐设备侧生成循环；是否是真实瓶颈要分阶段测量。[赛题](../../赛题选择.md)

| 操作 | 目标 |
| --- | --- |
| Top-K | 选出分数最高的 K 个候选，本身可以没有随机性 |
| Top-P | 根据累计概率阈值确定候选集合，集合大小动态变化 |
| Sampling | 按目标分布抽取 token，需要随机与统计验证 |

MoE 路由也用 Top-K，但候选规模、归一化和返回结果不同；有路由模板不证明已有通用词表采样。

## 先确定语义

固定输入 logits/概率、temperature、K/P 范围、过滤顺序、归一化、阈值交叉 token 的保留方式、并列值、输出顺序和索引类型。Top-K 后 Top-P 与相反顺序一般不等价。

覆盖 k=1、k=V、p=1、相同 logits、近单点分布、长尾及阈值附近概率。NaN/Inf、全屏蔽和非法参数按合同处理，不支持时明确拒绝。

PyTorch `topk` 不保证并列元素索引稳定；如果要求确定索引，要写明确 tie-break 参考，不能拿一次输出当唯一真值。[PyTorch topk](https://docs.pytorch.org/docs/2.15/generated/torch.topk.html)

## 算法路线

| 路线 | 优点 | 风险 |
| --- | --- | --- |
| 全排序 | 容易建立正确基线 | 成本、临时空间与后端支持 |
| 分块 Top-K 合并 | K 较小时可减少工作 | 全局语义、并列值、合并开销 |
| 阈值/分段选择 | 可能避免完整排序 | 终止条件和不能漏候选 |
| 无显式排序采样 | 有成熟 GPU 研究实现 | 随机源、控制流与分布正确性 |

FlashInfer 提供不显式排序的采样路线，说明排序不是唯一选择；其 CUDA 并行实现和速度不能直接套用。[技术文章](https://flashinfer.ai/2025/03/10/sampling.html)、[接口文档](https://docs.flashinfer.ai/generated/flashinfer.sampling.top_k_top_p_sampling_from_logits.html)

npu 已描述 sort/scan/reduce，但控制流有限。先验证最小排序/扫描探针；再确认随机源、种子、循环和后端可执行性。CPU 提供随机数、NPU 做抽样的分工若采用，应明确披露并确认题目允许。[SDK 分析](03-sdk.md)

## 成果如何收敛

若选定子题允许，可先交精确 Top-K 与样例接入，再扩展 Top-P/采样；若合同要求采样，则 Top-K 单独完成不能替代验收。高价值扩展是减少每 token 主机往返、连接连续设备路径、覆盖真实词表与 batch。

## 随机性验证

固定 seed 有助复现，但跨 PRNG、设备或并行顺序未必得到相同样本；若指定逐位随机合同则严格遵守。

- 小词表解析分布检查，非法候选不得出现。
- 多 seed、多次抽样，记录样本数、频率误差与置信区间。
- 预先选择 TV distance、分桶或合适的拟合优度检验；低期望频数不能机械套卡方检验。
- 同时验证确定性过滤结果和极端分布；统计通过不是数学证明。

性能覆盖多种词表、batch、K/P，并同时报告算子与生成循环时间，不能只展示最有利的形状。
