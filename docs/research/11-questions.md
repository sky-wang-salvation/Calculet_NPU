# 向工程师确认的问题

以下是从调研中产生的确认清单，尚未发送给主办方。优先解决会改变选题可行性的事项。

## P0：开始前必须明确

| 问题 | 为什么改变方案 | 当前证据 |
| --- | --- | --- |
| 五题与 SDK 的 A/B 路线是什么关系？ | 影响报名、交付与评审口径 | PDF 与公开页面表达不同 |
| 现场配套版本及可真机运行的最小样例是什么？ | 决定端到端链路是否可用 | README、STATUS 与快速开始有阶段差异 |
| 题一到四的接口、shape、dtype、参考实现和容差在哪里？ | 决定工作范围，不能自行降标准 | PDF 承诺有基线，但本次未取得各题验收包 |
| 哪些模块允许修改、哪些可公开提交？ | 决定项目组织和交付方式 | 公开可读与再分发许可不等同 |
| 设备时段、远程登录方式和故障处理由谁安排？ | 影响验证时间和执行边界 | PDF 写 5 台共用，用户转述每组开放设备 |
| Rust 构建机和树莓派部署机如何配合？ | Linux x86_64 工具链不直接证明 ARM 主机支持 | 快速开始与硬件架构不同 |

## P1：硬件与测量

- TOPS 的精度、稀疏性、计数方式和频率；NPU 的向量/归约能力。
- 双芯粒的内存组织、通信接口与开销；能否在同主机切换芯粒数。
- 树莓派实际 PCIe 宽度/速率、适配板与传输测量方式。
- 编译器与运行时允许的内存、对齐、动态形状和同步机制。
- profiler、设备事件、功耗读数是否可用，以及官方计时方法。
- 量化格式、舍入与特殊值行为；数值验收是容差还是逐位。

## 建议记录方式

每条答复记录日期、答复来源、适用版本、测试命令和证据路径。口头答复与实测结论分开保存，变更后更新选题卡和支持矩阵。

把问题按“阻止运行”“影响正确性”“影响优化”“影响展示”分组，优先用最小输入现场验证前两类。
