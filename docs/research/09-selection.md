# 选题决策与执行计划

## 基于条件的推荐

以下优先级是工程判断，不是官方评分预测。最先决定可行性的因素是**比赛提供的可运行基线、当前工具链和团队经验**。

| 团队能力/条件 | 优先考察 | 选择理由 | 开始前的门槛 |
| --- | --- | --- | --- |
| Rust、并行计算、数值基础较强 | 题一 | 单点边界清楚，容易建立正确性与性能证据 | 指定模式能编译、原始 NPU 基线能运行 |
| 算法与统计能力强，能写 kernel | 题二 | 有选择算法和设备协同的发挥空间 | sort/scan/reduce 与随机接口可用 |
| 熟悉 Transformer、愿意调试中间张量 | 题三 | 语义修复可直接扩展模型支持 | 固定小模型及一个可复现失败点 |
| 偏应用工程，已有检索基线 | 题四 | 任务可演示，质量指标清楚 | 至少一个完整核心模型/计算阶段可跑 NPU |
| 有模型移植经验、已有视觉基线 | 题五模型路线 | 可对接公开 SDK 强调的多模态生态 | 算子清单可收敛、权重和发射链路已通 |
| 熟悉编译/性能工具 | 题五工具路线 | 可帮助后续开发者定位问题 | 工具能接真实 NPU 执行并符合验收 |

缺少底层经验时，题四可能更符合团队能力，但**并不天然最简单**：若编码器后端不完整，它会退化为模型移植任务。类似地，已有成熟采样模板时题二也可能比从零做融合引擎更稳。必须先看实物基线。

## 每题最值得争取的一项成果

| 题目 | 建议聚焦的成果 |
| --- | --- |
| 一 | 一个被图实际调用的融合引擎，准确说明减少的中间读写 |
| 二 | 一个语义严格、能接生成循环的选择/采样模块 |
| 三 | 一个可定位、可复现、可回归的模型特性修复 |
| 四 | 一套质量与端到端延迟都可比较的本地检索/重排应用 |
| 五 | 一段完整可运行的新模型链路，或在真机上闭环的开发工具 |

## 报名前的四个判断

1. **入口**：有可运行样例吗？如果没有，谁负责提供、何时可以验证？
2. **增量**：相对已有模板，项目新增的到底是算法、语义、支持面还是集成？
3. **证据**：能否在有限真机时段内获得正确性、性能与 NPU 归因证据？
4. **退路**：主要假设失败时，是否有仍可独立验收的较小目标？

不建议一开始同时攻克新模型、新算子、新运行时和复杂前端。尽量让核心不确定性只有一个，其他层用已验证组件。

## 按阶段安排工作

| 阶段 | 应完成的事 | 继续条件 |
| --- | --- | --- |
| 环境验证 | 固定版本，tiny 编译→打包→执行→输出对照 | 有一次真实 NPU 正确结果 |
| 基线锁定 | 固定输入/模型/容差，测原始性能 | 能重复复现同一基线 |
| 最小增量 | 实现单个优化/适配或核心应用环节 | 功能与边界测试通过 |
| 真机评价 | 按同一协议进行 A/B 测试、收集日志 | 结果可解释，失败有记录 |
| 交付冻结 | 全新环境复现、文档、报告、演示 | 展示与仓库产物一致 |

在时间分配上，建议先预留约四分之一至三分之一的有效时间给真机验证与交付；这只是规划建议。共享设备排队时，本地准备独立参考、输入文件和自动报告，拿到时段后先跑最能排除可行性风险的探针。
