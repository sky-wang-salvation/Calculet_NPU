# schedule_01｜插件从“能接接口”推进到“能跟踪任务、拿到测试产物”

记录日期：2026-11-14（北京时间）。

对比基线：提交 `d3a7422` 的插件第一版，以及 [本机开发与交接](local-development.md) 中的上一阶段记录。本文件是 Harness 章节的第一份编号进度，保留原有记录，不改写历史测试结果。

**本轮结果：在 Windows 电脑上启动了官方 Harness 并确认插件运行；补上异步任务等待、可恢复查询、可读的结果文本，以及本机联调台的图片预览和下载。构建、类型检查及 22 项自动化测试通过，浏览器完成成功、失败、等待到时、刷新恢复和实际下载验证。使用的是测试服务，尚未接入真实模型或 NPU。**

## 1. 通俗理解：这次向前走了哪一步

上一版像一个已经接好按键的控制器：可以问“有哪些模型”、按下“开始”、再单独问一次“做完了吗”。但完整的等待、到时处理和结果查看还没有连起来。

这一版把这段使用过程接起来了：提交后能跟踪进度，等得太久可以先停下，稍后拿原任务编号继续查；完成后能看见测试图片，并打开或下载。

现在模型服务还没准备好，就用一个本机测试服务先检查这条链路。它返回带 TEST 标记的固定图片，只证明插件的任务和交付流程可以工作，不代表模型已经会出图。

“停止等待”只停止查询，不是取消后台生成。“刷新恢复”保留的是浏览器里的最后任务 ID；测试服务重启后，内存里的任务会清空。

## 4. 本轮测试结果

### 4.1 自动化检查

| 检查 | 实际结果 |
| --- | --- |
| `npm run build` | 通过 |
| `npm run typecheck` | 通过 |
| `npm test` | 19 项通过，0 失败 |
| `npm run test:integration` | 3 项通过，0 失败 |
| `git diff --check` | 通过 |

相比上阶段的 10 项，本轮总数增加到 22 项：新增 9 项跟踪／展示测试、3 项服务联调测试，并将原有注册测试更新为五项工具。测试数增加体现覆盖范围增加，不等于模型质量或性能提高。

覆盖的关键问题包括：

- 排队、运行到成功的多次查询只使用 GET，不重复提交生成。
- 等待到时仍保留 ID，同一任务可以恢复查询。
- 等待总预算包含卡住的 HTTP 请求，不会无限等下去。
- 后台失败、取消属于终态，但不被当成成功出图。
- 调用方中断后停止轮询；查询失败保留最近状态。
- 轮询期间模型、任务类型或执行模式异常变化会被识别。
- 非法等待参数提前拒绝；展示文本转义后端标签。
- 通过真实注册工具提交、等待、展示，再读取 PNG 字节和下载响应。
- 测试服务拒绝跨来源请求、非法输入和未就绪产物访问。

### 4.2 浏览器与宿主实测

| 操作 | 观察到的结果 |
| --- | --- |
| 打开官方 Harness 插件管理页 | `dsh-calculet-npu` 已启用，`calculet-npu` 组件显示运行中 |
| 普通测试任务 | 最终显示成功、TEST 图片预览、打开与下载链接 |
| 预设失败任务 | 显示 `FIXTURE_FAILURE`，没有成功产物 |
| 慢任务，设置 5 秒跟踪上限 | 显示等待到时，并保留任务 ID；任务仍可继续运行 |
| 刷新后点击继续跟踪 | 使用原 ID 取得成功结果和图片 |
| 点击下载测试产物 | 浏览器实际保存 `test-fixture.png` |

调用方中断停止轮询有自动化测试覆盖；本轮浏览器记录不另宣称已逐项验证所有停止时机。固定 PNG 的成功流程已验证，视频端到端尚未验证。

## 5. 改善了什么，尚不能说改善了什么

**已经改善的是使用完整性和出错后的恢复能力。** 提交、等待、查看、下载接成一条流程；等待到时与后台失败能分清；查询中断后保留编号，避免因不知道状态而重新生成。

**本轮没有证明推理更快、能耗更低或画质更好。** 测试服务的约 3 秒、约 15 秒是预设的协议测试时长，不是 NPU 推理耗时。没有性能 A/B 对比、真实模型输出、训练或反馈学习结果。

## 6. 当前运行与交付边界

- 本机环境：Windows、Node 24.14.0、npm 11.9.0、Harness `0.2.2-rc.3`。
- 本机有效开发目录和复现步骤见 [Windows 联调指南](windows-integration.md)。
- 验证时官方宿主位于 `127.0.0.1:3080`，测试联调台位于 `127.0.0.1:3081`；这不是对服务未来始终在线的承诺。
- 依赖镜像下载阻塞后，使用已下载缓存完成离线安装整理，并运行了官方 spawn-helper 检查及上述最终测试；没有升级系统 Node 或修改原锁文件。
- 测试服务始终声明 `simulation`，不加载权重、不执行模型或 NPU，也不调用云端生成服务。
- 图片预览界面位于独立联调台。Harness 插件输出可读文本和图片／产物引用；尚未增加官方聊天里的专用图片卡组件。
- 官方聊天仍需用户自行配置规划模型账号。本轮直接调用原生工具完成联调，没有验证自然语言模型的工具选择行为。
- 本轮功能、测试和进度文档一并纳入 Git 发布；依赖、本地配置、认证地址、截图及下载文件不纳入提交。

## 7. 下一步怎么接到真实模型

1. 模型团队提供一个完整验收的模型入口，明确输入参数、产物、错误和执行证据。
2. 按接口合同提供真实能力查询、异步提交、状态查询和产物访问。
3. 修改本地后端地址，重复这次的提交、等待、恢复、预览／下载检查，补测真实产物鉴权与浏览器可达性。
4. 配置规划模型后，验证用户一句自然语言能够触发完整工具链路。
5. 围绕选定用户任务再做反馈改进；真实性能、NPU 贡献和学习收益分别测量。

下一项关键成果是“真实 NPU 模型通过插件完成一次完整任务”，不是继续增加测试场景数量。
