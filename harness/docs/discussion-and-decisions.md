# 讨论记录与方案取舍

本文件整理对话中可见的需求、提案、用户反馈与取舍依据。按讨论顺序记录，不声称是逐字转录，也不把助手建议写成用户已接受的决定。

## 1. 方案演变

| 阶段 | 提案或需求 | 用户反馈/取舍依据 | 当前状态 |
| --- | --- | --- | --- |
| 起点：NPU 五题 | 算子、模型适配、检索与开放应用的研究 | 需要知道实际缺口、验证与可复用成果 | 基础技术研究保留 |
| 模型方向 | 生图模型迁移，另有 Cosmos/相关架构探索 | 用户要求本轮先同步进度，聚焦应用；不主动扩展架构研究 | 模型工程与应用设计分工 |
| 特别激励 | 企业赛道作品体现 Built for Better | 需要反馈后表现改善，能解释和回退 | 设计目标；资格流程未确认 |
| 第一轮应用脑暴 | 品牌创作、图解导师、办事图解、场景生成、分镜、执行助手 | 用户进一步明确想做的是 Agent 与少见 NPU 的桥梁 | 均降为候选，不视为最终产品 |
| 两个操作场景 | 调用已部署生成模型；用 Skills 辅助新模型部署 | 用户亲自迁移，可沉淀部署方法 | 作为技术工作流保留 |
| 反馈学习提案 | 经验记忆、Skill 改进、测试后晋升与回退 | 需要证明真实用户收益与商业价值 | 机制设计，尚无效果验证 |
| 商业假设 | NPU 厂商交付、内部创作团队、共享实验室 | 用户认为解释复杂，要求具体使用场景 | 待访谈，未确认买方和付费 |
| 简化成安装助手 | 少登录服务器、自动安装、记住修复 | 用户明确指出安装包、补丁或 Skill 就能解决，不需要把它当独立产品 | **作为主要卖点被否定** |
| 回到任务价值 | 围绕用户结果，列问题、方案、NPU 核心计算与优化 | 用户要求重新读 PDF，用表格和思维导图说明 | 已形成三场景文档，仍未选定 |
| 本次归档 | Edge 调研与 Harness 讨论分别建立入口和交接 | 用户要求放入 Cosmos 3，并把 Harness 讨论新开章节上传 | 本次整理任务 |

## 2. 提出过的六个应用方向

| 候选 | 用户任务 | 可能学习的内容 | 尚未解决的问题 |
| --- | --- | --- | --- |
| 品牌创作搭档 | 做视觉提案、配图 | 偏好、漏项、可靠创作流程 | 相比现有工作流的额外收益、付费需求 |
| 图解导师 | 解释知识或操作步骤 | 误解与有效解释方式 | 等价题评价、实际学习效果 |
| 办事图解助手 | 把复杂说明变成分步指引 | 容易误解的表达和步骤 | 用户能否更容易完成任务 |
| 场景生成工坊 | 围绕失败条件生成测试候选 | 漏测条件、有效场景配方 | 模型控制能力和独立有效性评价 |
| 故事/分镜助手 | 脚本到可评审视觉材料 | 设定约束和遗漏检查 | 完整出图、连续一致性、返工收益 |
| 多模态执行助手 | 自动组织生成任务 | 流程可靠性和失败条件 | 是否优于脚本；不能只把缓存变快算学习 |

这些方向均为助手提出的候选。用户没有确认采用其中任意一个，后续文档不得写成“已定产品”。

## 3. 已排除的价值表述

- “写一层聊天入口，就形成了独立商业产品。”现有接口和工作流是现实替代方案，需要额外的任务收益。
- “把上次问题存成记忆/Skill，就是足够的自进化价值。”用户明确反对把可封装的固定工作当主要需求。
- “NPU 少见，所以一定有大市场。”设备数量、客户任务和预算均未验证。
- “用了 NPU 就一定更快、更省电、更便宜。”没有同条件测量不能作此承诺。
- “有界面或图片就证明 NPU 已完成目标模型。”需实际执行、正确性和分工证据。

上述排除不否定 Skills、安装包、脚本的工程用途。它们继续作为实现组件，不取代用户需求验证。

## 4. 当前可以沿用的结论

1. 用户希望继续探索 DeepSeek Harness 与 NPU 的桥接。
2. 能力调用、部署适配与反馈学习可以分层组织，但最终必须服务一个明确任务。
3. 当前最需要补齐的是“具体用户—问题—方案—NPU 工作—验证—采用理由”，而不是继续增加平台名词。
4. 用户体验收益、硬件收益、内核优化收益、学习收益应分别评价。
5. 商业客户、最终应用、定价、训练能力、自治范围及完整接口均未定。

## 5. 商业假设的状态

讨论过芯片/整机厂商为减少重复交付工程付费、已有本地设备的创作团队为减少操作与返工付费、实验室作为试点。这些只有逻辑上的候选理由，没有客户访谈、付费试点、市场规模或产品收入证据。

候选的收费方式也只是讨论，不能作为已验证商业模式。尤其安装/部署作为独立卖点已被用户否定，后续不能仅换名后重新当作已认可路线。
