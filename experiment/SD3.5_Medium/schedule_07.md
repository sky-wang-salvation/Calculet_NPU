### 2.2 NPU 返回值确实进入真实生成链

```text
CPU：CLIP 文本编码及去噪上游
    ↓ 真实隐藏状态 [1,256,1536] 转 BF16
NPU：首层 transformer_blocks.0.attn.to_q
    每次拆成 16 个 M16 tile，覆盖全部 256 行
    ↓ 返回值恢复框架 dtype，进入真实 forward
CPU：其余 DiT、scheduler
    ↓ 重复 4 步
CPU：VAE 解码 → PNG
```

归档报告的步骤 0—3 分别关联请求 1—4，冻结生成源码的 `forward` 替换与 callback 检查与该关系一致。因此它不是旁路跑一次 Q 探针后另行生成纯 CPU 图片。

| 范围 | 归档记录 |
| --- | --- |
| NPU 请求 | 4 次。 |
| tile | 每请求 16 个，共 64 个；起始行为 0、16、…、240。 |
| 计算段策略 | 显式 `dort`、`allow_pending=false`、strict、空 allowlist。 |
| 计算段回退 | 64 个 tile 的前后记录与聚合计数均未报告 CPU fallback / host implementation 调用。 |
| 历史设备关闭 | 该次四个请求均记录 `device_closed=true`；不代表当前设备状态或扩大版已释放。 |
| CPU 分工 | CLIP、其余 DiT、scheduler、VAE、BF16 边界转换、行拼装与传输组织。 |

**计算段零回退不等于整条应用没有 CPU 计算。** 每步调用一次 NPU，也不能推导 NPU 已承担大部分 FLOPs 或主要延迟。

## 3. NPU 覆盖扩展：代码候选与真实覆盖分开

扩大版候选代码包含：

- 对 392 个 `torch.nn.Linear` 候选进行清点与绑定。
- BF16 权重 / 偏置预算常量为 `4,486,127,744` 字节。
- 设备池配置常量为 `8 GiB`。
- 常驻参数上传、M16 分块、运行记录、实际调用模块清单和清理逻辑。

**这些是静态代码事实，不是已实现的设备覆盖或实测内存。** 客户端区分“注册候选”与“实际调用”，结束条件也不保证全部 392 项均已执行。只有取得本次运行的实际调用清单、返回值去向、数值与最终产物，才能报告扩大后的真实覆盖。

即使该扩大路线后续成功，候选实现仍保留以下 CPU 范围：Attention QK / softmax / PV、归一化与激活、卷积与位置处理、CLIP、VAE 和 scheduler。因此不能称为完整 DiT NPU。

原会话中的后台任务停止通知，仅表示客户端任务跟踪没有完成记录，不能证明远端已经终止或释放设备。旧 Q-only 请求的关闭回执也不能用于扩大版。

本快照不公布“1/392”之类全模型覆盖百分比：模块数量、算量、延迟占比和最终质量是不同指标。
