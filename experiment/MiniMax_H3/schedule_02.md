## 2. 当前已确认的部署认识

延续 schedule_01 的核心结论：

```text
HF 权重／配置 → 图像推理前端及 Dope 接入 → 厂商运行时 → Calculet NPU
```

- 套件 README 已明确：现有 vLLM 路径读取 **HF 权重＋Dope 后端，不读取 calbin**。因此 tiny 的 `.cvxo → calbin` 实验不是这条 HF 接入路径的必经前置。
- 现有单双芯服务脚本针对 **Qwen 文本生成**，不能只替换模型目录就宣称支持 H3-Image；普通 vLLM 插件不能等同于 vLLM-Omni／Diffusers 的图像流水线支持。
- 如果一般 PyTorch 执行与目标算子可用，优先评估 Diffusers → Dope 的接入；如果实际只有指定 LLM 路径，则需要补图像前端或模型执行适配。**目前没有完成该分支判断。**
- 不先安装 Rust 或强行走静态 calbin，也不先升级原厂 venv 中的 vLLM、Torch、Triton。是否需要额外编译工具和隔离环境，由实际执行路径决定。
- MiniMax 上游的 CUDA／昇腾教程不能直接作为 Calculet 的部署成功证据。

## 4. 当前技术阻塞项

### 4.1 接入能力：HF＋Dope 不等于任意图像模型受支持

需要将 H3-Image 的具体计算路径与现有后端能力对齐，包括文本条件、DiT、图像 VAE，以及 Attention、RoPE、归一化、卷积、布局和 BF16／FP32 处理。不能仅凭包名、注册条目或 Qwen 的异机实测判断全部覆盖。

下一步优先使用已经取回的注册与回退证据，定向补读设备注册入口及执行实现；只有当前证据包没有的部分才补采集，避免反复要求相同资料。

### 4.2 容量：需要加载与运行计划，而非只看权重总大小

上游核心组件权重文件合计约 135 GB；DiT 单独约 66.28 GB，另有文本编码器和图像 VAE。目标板卡日志报告总量 64 GiB，主机 RAM 的前序报告约 59 GiB。

- GB 与 GiB 不能混用；文件总大小也不等于必须同时常驻的运行内存。
- 仍需核对有效加载范围、设备保留区、激活／工作区和组件生命周期。
- 不能仅凭这些数字承诺一定能跑，也不能未经加载计划分析就宣称绝对无法运行。
- `POOL_BYTES=8 GiB` 是示例执行池配置，不是物理容量；调大它不等于扩容。
- CUDA 框架的 offload 能力不能直接推定在 Dope 上成立，必须验证实际支持。

### 4.3 贡献：允许如实描述混合执行，不把回退出图冒充完整 NPU 迁移

回退名单的存在提示：即使程序最终产出图片，也需要明确哪些阶段真实在 NPU 上、哪些算子回退 CPU，以及同步和搬运开销。注册表 accept、HTTP 服务启动、CPU 兜底或远程 API 出图，都不是完整 NPU 模型验收。

## 5. 接下来围绕“跑通模型”的执行顺序

以下是待执行计划，不是本次完成结果；涉及设备的部分必须先获得明确使用窗口。

| 阶段 | 具体目标 | 应留下的证据 |
| --- | --- | --- |
| 后端路径确认 | 对齐 PyTorch 设备入口、前端依赖和实际执行方式，列出第一个阻塞项 | 原文位置、版本、最小复现方案，明确未知项 |
| 最小真机验证 | 在获准窗口内确认原厂样例本机可复现，并验证一个 H3-Image 所需的关键算子或子模块 | 真实设备执行记录、参考输出和误差比较、回退范围 |
| 必要适配 | 按实际失败点补算子、布局、dtype 或桥接；适配后立即做回归 | 改动、边界用例、参考结果与设备结果 |
| 模型模块串联 | 逐步接通文本条件、DiT 去噪和图像 VAE，不一开始就盲目加载全部权重 | 各阶段输入输出合同、内存计划、执行轨迹 |
| 完整本地出图 | 固定模型版本、详细英文提示词、seed、batch 1 和原生 6 步；初始目标 2048×2048 | 有效图片、设备日志、CPU／NPU 分工、可复现命令 |
| 跑通后优化 | 有正确基线后再定位瓶颈，不虚设加速倍数 | 编译／加载／预热／推理分开计时，质量与资源对照 |

子模块验证是整模型迁移的中间步骤，不代表改报算子题，也不能宣称局部成功就是整模型完成。当前不额外承诺 ComfyUI、复杂服务或多尺寸工作流，先让固定的本地单图流程成立。
