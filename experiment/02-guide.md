# 02｜我的实验引导思路：本地准备、NPU 真机跑通，再做优化

整理日期：2026-11-14。

本文记录我的模型迁移目标、实验顺序，以及本地 Linux 与 NPU 真机的协作方式；它是实验方法指南，不是某个真实模型已经上板成功的报告。环境安装与 tiny 的具体复现命令见 [01-setup.md](01-setup.md)。

## 1. 我的目标：先迁移跑通，再优化

我希望实现两件事：

1. 将原来在 NVIDIA GPU 上运行的模型迁移到 Calculet NPU，让模型的核心计算能够实际在 NPU 上执行。
2. 先让目标模型在真机上完成推理、得到可核对的结果；跑通后，再优化速度、内存和并行效率。

因此，我采用的顺序是：**先完成必要适配并建立正确性基线，再围绕这个基线做性能优化。**

第一版可以慢一些、实现朴素一些，但不能只做到下载代码、装好 CUDA、编译成功或程序启动。它必须逐步走到目标模型在 NPU 真机上的完整推理。

这里的“本地预处理”是对本地准备工作的概括，实际包括模型分析、算子适配、权重转换、编译和打包；不是简单处理一下输入，就能把现有 CUDA 程序直接搬到 NPU。

## 2. 先分清三个执行位置

“真机”通常指有 NPU 板卡的主机及其设备环境，而不是能登录 NPU 芯片后直接运行 Python。为了避免混淆，我把工作分成三层：

| 位置 | 负责的事情 | 单凭这一层的结果不能证明什么 |
| --- | --- | --- |
| 本地 Linux 开发环境 | 阅读原模型、准备参考结果、实现必要适配、转换权重、编译 CalVX、生成 calbin、离线检查 | 不能证明 NPU 已执行、数值正确或性能达标 |
| 板端主机，也就是连接 NPU 的服务器 | 核对设备与运行时、部署完整产物、准备并送入输入、发起执行、等待完成、读回输出和日志 | 文件上传成功或部署完成，不等于计算正确 |
| NPU 设备 | 执行编译生成的设备程序，完成已经映射到 NPU 的算子与核心计算 | 设备执行结束，也仍需用参考结果检查正确性 |

同一台 Linux 主机也可能兼任开发机和板端主机。区分它们是为了明确职责，不是要求一定准备两台电脑。

必要的分词、输入解码、图像预处理、调度和输出后处理可以在主机上执行；但必须明确计算边界，不能把主要计算仍留在 CPU/GPU 的结果当作核心计算已迁移到 NPU 的证据。

## 3. 本地 Linux 可以先做哪些准备

### 3.1 固定原模型与实验输入

在移植前明确：

- 使用哪个模型、源码版本和权重版本，确认权重格式、获取权限及许可。
- 第一次验证采用什么 batch、输入尺寸或序列长度，以及数据类型。
- 使用哪份固定输入；涉及随机性时记录随机种子和相关配置。
- 原模型的输入预处理与输出后处理是什么，避免 NPU 与参考端处理的不是同一份数据。

第一阶段可以选择较小 batch、固定尺寸等最小可行配置，但不能以一个 toy 模型或单个算子代替目标模型，然后宣称目标模型已经迁移完成。

### 3.2 准备参考输出，而不是只看“有输出”

在原模型能够正确工作的框架和环境中，保存固定输入对应的输出；必要时再保存关键层的中间结果，供定位误差使用。

- 原模型能在 CPU 正确运行时，可以用 CPU 产生参考。
- 原实现强依赖 CUDA 时，可以在另一个可用的 NVIDIA 环境产生参考，不要求所有工作都发生在自己的开发机上。
- 完整模型的 CPU 参考成本太高时，先准备小尺寸、关键算子或子图的参考，再补齐完整推理的比对方案；子图参考不能代替完整模型的最终验收。

NPU 的交叉编译和打包不等于运行原 CUDA 模型。没有本地 NVIDIA 显卡，并不妨碍进行源码分析、权重处理和本章示例中的离线构建，但会影响如何取得原实现的参考结果。

### 3.3 分析算子，补齐“能运行”所必需的适配

梳理模型的计算图、算子、shape、dtype 和张量布局，把它们分为：

| 情况 | 第一阶段怎么处理 |
| --- | --- |
| SDK 已有满足语义、形状和精度要求的实现 | 尽量复用，并接入模型的执行路径 |
| 已有实现，但接口、布局或形状不匹配 | 做必要适配，不直接假定同名算子完全等价 |
| 没有可用的 NPU 实现 | 先实现简单、正确且可编译执行的版本，再考虑优化 |
| 必要原语或后端能力不明确 | 用最小例子验证；若确实受阻，保留错误并向 SDK 提供方确认可行路径 |

CUDA kernel、Triton kernel、CUDA 扩展和 TensorRT engine 不能默认直接复用。需要依据这套 NPU SDK 的表达方式，替换对应计算实现并接入模型；仅安装原来的 Python 依赖不等于完成迁移。

**缺失算子、权重布局、运行接口、必要的精度处理和设备容量适配，都属于“先跑通”的第一阶段，不应推迟成“以后优化”。**

### 3.4 转换并组织真实权重

从模型原始检查点读取权重，按目标实现需要进行：

- 张量命名与形状映射。
- 存储布局、分块和对齐处理。
- 必要的数据类型转换；涉及量化时，同步处理 scale、zero point 等语义及误差。
- 按目标设备和程序的并行方式切分权重。
- 检查最终参数块与设备程序声明的布局、大小和寻址是否一致。

`tiny-pack` 只是 tiny 示例的测试权重生成器，不是任意模型的通用转换器。tiny 中每芯粒一个 `param_blk` 文件的做法，也不能不经核对就推广为所有模型的固定打包布局。

### 3.5 编译、原生生成和离线检查

在匹配的 Linux 构建环境和 SDK 下完成：

1. 将 NPU kernel 与完整程序入口编译为 CalVX。
2. 将完整程序与相应权重交给 `docc`，生成目标板的原生产物并打包为 calbin。
3. 使用 `docc calbin doctor` 检查清单、引用文件和命令流等结构性问题。
4. 保存编译错误、打包结果和检查警告，避免把失败留到共享真机上才首次发现。

这个阶段不需要把设备启动起来，但离线检查也不能证明数值正确、设备容量足够或连续执行安全。

## 4. 从本地交给板端主机的应该是什么

不是只上传一个 `.cvxo`，也不是把原来的 CUDA 二进制复制过去。应交付一套能对应同一次实验的材料：

| 交付项 | 用途 |
| --- | --- |
| 完整的 calbin 部署产物 | 包括清单、原生程序、命令流和所需参数块等，具体以 SDK 包结构为准 |
| 主机侧启动与输入/输出处理代码 | 负责调用运行时、组织输入、执行必要前后处理；不能假定权重包替代全部应用逻辑 |
| 固定测试输入与配置 | 让真机处理与参考端一致的数据、shape、dtype 和随机配置 |
| 参考输出与比较口径 | 判断结果是否正确；需要时提供中间层参考 |
| 版本及文件对应关系 | 记录源码、SDK、权重来源、转换配置与构建结果；重要文件保留 SHA-256，防止两端使用不同版本 |
| 已知问题与运行限制 | 例如缓冲区复用警告、固定输入约束、尚未覆盖的形状，不能只传“成功”的结论 |

本章所说的“推送到真机”，是传输并部署实验产物，和把文档或代码 `git push` 到 GitHub 不是同一件事。无论用哪种经授权的传输方式，传输完成后仍需在板端主机执行和验证。

## 5. NPU 真机侧需要做哪些事情

### 5.1 板端主机：先确认运行条件

- 获得分配的设备编号、访问权限及使用窗口，确认驱动和运行时与部署产物匹配。
- 按实际设备能力确认内存、地址布局和程序配置，不只看开发机上的静态检查结果。
- 检查收到的文件、版本和哈希，保证它们与本地参考所用权重、输入一致。
- 在共享账号或共享设备环境中，先协调资源归属；不能因为没有锁文件，就认定板卡或其他人的服务可随意使用。
- 使用约定的板锁机制，不擅自停掉未知任务、容器或服务。

使用者说明目标硬件是两芯粒、每芯粒 16 核；SDK 示例中的 `cores = 2` 与硬件核数的映射仍需按 SDK 语义确认，不能机械改成 `16`。

### 5.2 板端主机与 NPU：实际部署、执行、读回

板端主机把包和输入送到设备的正确位置，通过 `dort` 等配套运行接口发起计算，并等待执行结束。NPU 负责实际执行映射到设备上的计算；完成后，主机再取回输出和必要日志。

第一次采用固定输入、最小可行配置和受控的单次执行，检查真实部署位置、返回状态及输出文件，而不是只看一句“部署成功”或“run finished”。

如果存在 ping/pong 同址等风险，先明确限制和执行行为，不直接开启连续、流水或并发测试。单次执行也必须实际验证，不能因规避了多轮场景就认定问题已经修复。

### 5.3 读回结果后：先判断正确性

对照同一输入、同一权重的参考结果：

- 检查输出的形状、类型、有效范围和有限性。
- 按正确的位置提取有效输出，不能把额外工作区或调试空间当作模型结果。
- 根据算子语义、精度和验收要求比较误差，不擅自固定一个通用容差，也不一律要求逐字节相等。
- 发现差异时，结合中间层结果定位输入处理、权重布局、算子实现或同步问题。
- 将完整运行日志和有效证据带回本地，与对应构建版本一起保留。

在确认单次正确、缓冲区复用安全后，再逐步增加重复运行与其他输入检查，判断是否具有可重复的功能正确性。

## 6. 用 tiny 理解这次协作，而不是把 tiny 等同于模型迁移

以下仅归纳本对话中已经提供的 tiny 终端记录；更完整的命令和输出见 [01-setup.md](01-setup.md)，不表示这里重新执行过这些操作。

| tiny 环节 | 发生在哪里 | 说明 |
| --- | --- | --- |
| `tiny-pack` 生成两块测试权重 | 本地 Linux | 证明示例权重生成器可运行；不等于真实模型权重已经转换 |
| `tiny-ref` 对 token `7` 生成 CPU 输出 | 本地 CPU | 得到 `1024` 字节的 bf16 参考输出，供后续同输入比对 |
| 启用 `step` 后生成 `.cvx` / `.cvxo` | 本地 Linux | 完整示例程序能生成 CalVX；不是已经执行设备程序 |
| `docc` 生成 calbin | 本地 Linux | 后续检查实际发现了 4 个 CCU ELF，说明原生产物生成链路可用 |
| `doctor` 报告拒收 0、警告 3、不可解码稳态流 0 | 本地 Linux | 硬性完整性检查通过，但仍有三个张量的 ping/pong 同址警告 |
| 将同一输入送到 NPU 并比较输出 | 本次 tiny 对话记录中尚未完成 | 不能仅凭前面步骤宣称 NPU 数值正确或性能达标 |

tiny 已经具备示例的 kernel、程序入口、权重工具和 CPU 参考。我在这个例子中先验证了工具链；面对一个新的 NVIDIA 模型，还需要完成它自己的模型与算子适配、真实权重转换和验证工作。

## 7. 第一阶段“先跑通”的完成标准

第一阶段以最小可行配置完成以下目标：

1. **是目标模型的完整推理。** 算子或子图可以作为中间里程碑，但不能代替完整模型的最终目标。
2. **使用对应的真实权重和明确输入。** 不能把 tiny 的随机测试权重或任意占位数据当成目标模型的迁移结果。
3. **核心计算实际在 NPU 执行。** 清楚说明主机端的必要前后处理，以及是否仍有未迁移的核心计算。
4. **输出通过适当的正确性检查。** 不只要求“有输出”，而是与参考结果比较并解释必要的数值差异。
5. **过程可复核。** 保留构建、部署、输入输出、版本和已知限制，并在安全条件下检查可重复性。

第一版允许性能不理想、调度朴素、只覆盖明确的输入配置；但执行失败、数据覆盖、核心计算未迁移或数值不正确，不能用“后面再优化”带过。

## 8. 第二阶段“再优化”的工作

先冻结第一阶段的正确性基线，再测量瓶颈并逐项修改，例如：

- 优化算子实现、融合计算，减少中间结果的读写与启动开销。
- 在 SDK 支持和语义明确的前提下，改善多核、多芯粒并行及通信。
- 优化内存布局、复用和传输，减少不必要的数据搬运。
- 优化主机调度与应用端开销，区分 NPU 执行时间和端到端耗时。

每次修改都要重新检查数值正确性，再比较相同输入、配置和计时边界下的性能。不能只展示加速数字，而不说明精度、计算范围或数据是否变化。

如果内存容量、数据类型或布局问题已经阻止模型运行，解决它们属于第一阶段的必要适配；不是所有涉及性能或内存的改动都能推迟到第二阶段。

## 9. 我的推进方式：小步上板，而不是一次性交付

总体循环是：**本地准备和适配 → 部署到分配的板端主机 → NPU 执行与结果比对 → 把问题带回本地修改 → 再次上板验证。**

不必等整个大模型全部改完才首次上板。尽早选取关键算子或最小子图验证后端可用性和数值语义，然后逐步接入完整目标模型；但始终明确，中间子图成功并不等于完整模型已经迁移成功。

| 发现问题的环节 | 主要处理方向 |
| --- | --- |
| 本地编译失败 | 修复 SDK 接口使用、静态形状、类型或 kernel 表达等问题 |
| 原生生成或 doctor 检查失败 | 检查程序入口、权重布局、清单、文件和后端支持 |
| 真机部署或执行失败 | 结合日志核对设备选择、运行时、内存、地址、同步及输入约定 |
| 真机输出与参考不一致 | 先定位输入预处理、权重转换、算子精度/语义和数据覆盖，再谈性能 |
| 完整推理正确但速度不理想 | 进入第二阶段，先测瓶颈，再做有证据的优化 |

## 10. 我的实验原则

- 本地准备服务于模型真正迁移，不把装环境或调研当成最终成果。
- 必要适配和迁移一起推进，不预设存在能自动转换任意 CUDA 模型的工具。
- 先让最小配置下的完整模型在 NPU 上正确运行，再扩大输入范围和优化性能。
- 区分下载成功、编译成功、打包成功、静态检查通过、真机执行成功和数值正确，不把它们混为同一个“跑通”。
- 保留失败、警告和未验证项，让下一次本地修改与上板验证能够对应同一份实验。

**一句话总结：我在本地 Linux 完成模型迁移所需的准备与适配，在 NPU 真机上验证真实执行和正确性；先得到可信的完整推理基线，再逐步优化。**
